## A. BLOCKER (#3) — F-01 is half-fixed: "latest" now means last-inserted, not newest

`get_latest_prices()` and the `latest` CTE in `get_all_items_with_prices()` both
rank with:

```sql
ROW_NUMBER() OVER (PARTITION BY ph.vendor_id ORDER BY ph.created_at DESC, ph.id DESC)
```

That trades day-precision `date_recorded` for **insertion order**, which is a
different wrong clock. `add_price()` now takes a `date_recorded` argument
specifically so history can be backfilled — and any backfill inserts an old row
with a new `created_at`, so the old row wins.

`python3 docs/repro/f01_backfill.py`:

```
CURRENT (created_at only):
    -> recommends Sysco @ $18.0 (dated 2026-08-14)
FIXED (date_recorded first):
    -> recommends Sysco @ $22.0 (dated 2026-08-21)
```

Today's real Sysco price is $22.00. Re-import one week-old invoice and the Order
Guide quotes $18.00 as Sysco's current price — and prints the stale date next to
it. This is F-01's exact failure mode (recommend a superseded price) through a
different door. Triggers on: re-importing an emailed sheet, a scraper catching up
after downtime, a manager keying in last week's invoice.

You already knew this coupling existed — `scripts/init_db.py` carries the comment
`# Oldest first: insert order defines which row is "latest"`. That's a
load-bearing comment: correctness now depends on every writer inserting in
chronological order, forever, and nothing enforces it.

**The test suite has a blind spot on exactly this axis.**
`tests/test_database.py::test_old_history_still_excluded` looks like it tests
date semantics but inserts 2020 then 2026 — chronological, so it passes either
way. Reverse the two inserts (`python3 docs/repro/f01_test_blindspot.py`):

```
rows: [{'vendor': 'Sysco', 'price': 10.0, 'date_recorded': '2020-01-01'}]
test asserts price == 20.0 -> FAIL (got 10.0, a 2020 price)
```

**Fix** — in both queries:

```sql
ORDER BY ph.date_recorded DESC, ph.created_at DESC, ph.id DESC
```

`date_recorded` decides which sheet is newest; `created_at`/`id` break same-day
ties, which is all F-01 ever needed them for. Then reverse the inserts in
`test_old_history_still_excluded` so it actually tests the date axis, and add a
backfill case: insert today, then insert last week, assert today's price wins.

## B. BLOCKER (#4) — F-04's tile guard is close to a no-op on this catalog

`_tile_matches_item()` accepts when `hits >= max(1, len(item_tokens) // 2)`.
Floor division means a 2-token *and* a 3-token item name both need **one** token
to match. Tokens shorter than 3 chars are dropped, so the grade/size numbers that
actually distinguish SKUs (`80/20`, `40%`) vanish before comparison.

`python3 docs/repro/f04_tile_matcher.py` — every item below is real in `sample_items`:

```
MATCH   Whole Milk              <-  Whole Wheat Flour 50lb Bag
MATCH   Ground Beef 80/20       <-  Ground Turkey 93/7 Lean
MATCH   Ground Beef 80/20       <-  Ground Beef 73/27 Bulk
MATCH   Chicken Breast          <-  Chicken Thighs Boneless
MATCH   Heavy Cream 40%         <-  Heavy Duty Foil Wrap
MATCH   Atlantic Salmon         <-  Atlantic Cod Fillet
reject  Olive Oil Extra Virgin  <-  Canola Oil 35lb
```

6 of 7 wrong products accepted. Heavy Cream matching foil wrap is the tell. The
guard stops position-zero sponsored tiles (which is what the existing tests
check) but not the near-miss neighbours a food-vendor search page is *full* of —
and a wrong-product price feeds straight into the recommendation and the savings
math.

**Fix** — `docs/repro/f04_proposed_matcher.py` scores 14/14: the false positives
above plus seven true positives that must keep matching.

```python
def tokenize(text):
    # keep numeric tokens: '40', '80', '20' are what separate SKUs
    return [t for t in re.findall(r'[a-z0-9]+', text.lower())
            if len(t) > 2 or t.isdigit()]

def _tile_matches_item(tile_text, item_name):
    item_tokens = tokenize(item_name)
    if not item_tokens:
        return bool(tile_text and tile_text.strip())
    tile_tokens = set(tokenize(tile_text))

    # Every numeric/grade token must appear: 80/20 is not 73/27
    numerics = [t for t in item_tokens if any(ch.isdigit() for ch in t)]
    if any(t not in tile_tokens for t in numerics):
        return False

    words = [t for t in item_tokens if t not in numerics]
    hits = sum(1 for t in words if t in tile_tokens)
    if len(words) <= 3:
        return hits == len(words)            # short names: require all words
    return hits >= math.ceil(len(words) / 2)  # ceiling, not floor
```

Your existing five tile tests all still pass under this. Add the seven rejects
above as cases — they're the ones that matter.

Judgment call, low priority: `test_partial_overlap_still_accepted` asserts
`'Heavy Cream Whipped Topping'` matches `'Heavy Cream'`. Whipped topping is a
different product at a different price. The proposed matcher still accepts it
(both words present); catching it needs product-identity matching, which is a
bigger job. Worth a comment noting it's deliberate.

## C. HIGH (#5) — the AI ingestion boundary still trusts the model's arithmetic

`parse_document()` wraps parsing in `except json.JSONDecodeError`, but the
per-item coercion `float(item['price'])` sits **inside** that try and raises
`ValueError`, which nothing catches. One `"N/A"` or `"$24.50"` in a
model response and the whole document raises out of `parse_document` into
`email_monitor` — every other item on that sheet lost. The prompt asks for
"Numeric value only ... as a number not string", which is hope, not validation.
Note `add_prices_batch()` gets this right with a per-row savepoint and
try/except; `parse_document` should match it.

Two related gaps on the same boundary:

- **No price bounds anywhere.** `0`, negative, and `1e9` all insert cleanly, then
  win `get_latest_prices` and poison savings. Add `CHECK(price > 0)` to
  `price_history` in `scripts/schema.sql` plus a sane ceiling in the validator.
- **`_resolve_item_id()` auto-creates items from model output.** A garbled PDF
  silently expands the catalog with hallucinated product names. On the
  email/scrape path, prefer matching an existing item and route unknown names to
  a review list instead of `INSERT`ing them.

## D. MEDIUM (#5) — the auth gate is correct only by accident

`require_login()` reads `os.getenv('APP_PASSWORD', '')` directly, but nothing in
`auth_gate.py` imports `core.config`, and `load_dotenv()` runs at
`core/config.py` import time. Today it works because every page happens to
`import core.database` (→ `core.config`) further down its import block. A page
that imports only `auth_gate`, or an import reshuffle, means `.env`'s
`APP_PASSWORD` reads as empty — and empty is the **fail-open** branch: warning
banner, page renders. Use `Config.APP_PASSWORD` (already defined, currently
unread) so the gate can't depend on someone else's import.

Also: unlimited password attempts with no delay or lockout. For a homelab that
may be an acceptable risk — but say so in the README rather than leaving it
unstated.

## E. MEDIUM (#4) — parse the From header with the stdlib

`_is_vendor_email()` hand-rolls `address.rsplit('@', 1)[1].rstrip('>.')`. The
exact/subdomain comparison is the right fix for F-09 and it holds for the obvious
spoofs, but header parsing has more edge cases than a `rstrip` covers. Use
`email.utils.parseaddr(from_address)[1]` and keep your domain comparison on the
result. Worth noting in the README: domain trust with no DKIM/SPF check means
anyone who can spoof the sender gets a PDF ingested as vendor pricing.

**1. Merge the stack before opening anything new.** Four PRs deep, nothing
merged, `master` still at `35fa5ef`. Every branch is a linear child of the last,
so review cost compounds and any `master` change means four rebases.

**2. Merge order is #2 → #3 → #4 → #5, and do not squash.** All four target
`master` and all report MERGEABLE, which is misleading — they share commits.
Squash-merging #3 rewrites `1835f7f` into a new SHA and #4 and #5 will conflict
against the commit they contain. Use merge commits (or rebase-merge) and land
them in order; #4 and #5 will visibly shrink as each parent lands.

**3. Fix A and B on their own branches first** (#3 for A, #4 for B), so the
history shows the finding fixed where it was claimed rather than repaired two PRs
later.

real, tested, and green — and each test exercised only the axis where the fix
already worked. F-01's test inserted in chronological order; F-04's tests used
obviously-unrelated tiles. For anything money-facing, write the adversarial case
first (reversed order, near-miss neighbour, malformed field) and watch it fail
before you fix it. Cheap here: no venv, no API key, no browser — `schema.sql`
plus stdlib `sqlite3`, as the four scripts in `docs/repro/` do.

**5. Update `docs/CODE_REVIEW.md` as findings land.** With 40 numbered findings
across four branches, a status line per finding (open / fixed in #N / won't fix)
is the only way to know what's left. Right now that lives only in PR
descriptions. And on the strength of A and B, `docs/CODE_REVIEW.md` should not
mark F-01 or F-04 fixed yet.
